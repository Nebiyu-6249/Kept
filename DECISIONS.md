# Decisions

Where the build specification was silent, this is what was decided and why.
One entry per decision, in the order they came up.

---

## Data model

**Three models beyond the specified schema.** `ImportRow`, `Correction` and
`ImportRow`'s state enum are not in §5, but §8 specifies that
`GET /api/import/[batchId]` returns `rows`, and §7.3 specifies storing
correction pairs — neither is representable without somewhere to put them.

**`@@unique([userId, label])` on `Bill`.** §8.2 says the sweep should "upsert
Bill", which needs a unique key to upsert against.

**Categories are upserted, never deleted, by `PUT /api/policy`.** Transactions
carry a `categoryId`; deleting a category the user removed during a policy
rewrite would orphan history they can still see in the ledger.

**Rules are replaced wholesale on a policy rewrite.** Safe because
`Intent.ruleRef` is a plain string rather than a foreign key, so a verdict that
cited `R-03` keeps its citation after the policy changes. What the rule said at
the time is preserved in `Intent.reasoning`.

## Domain logic

**`daysRemaining` counts whole days *after* today.** On the last day of a
period it is 0, which reads as "the period ends today". §6.2 fixes
`projectedEndSpend` as `spentTotal + dailyBurn * daysRemaining`; defining
remaining this way — with `daysElapsed` counting today — makes that formula an
exact run-rate projection instead of one that over-projects by a day.
`daysElapsed + daysRemaining === daysTotal` always holds.

**A bill is "committed" when its due date has not passed.** §6.2 says
"active bills due before period end, unpaid" without defining unpaid. A bill
already due inside this period has its payment sitting in `spentTotal`;
counting it again would charge the user's own money against them twice.

**`SEMIMONTHLY` splits on the anchor and 15 days later; `WEEKLY` treats
`periodAnchor` as an ISO weekday** (1 = Monday). §6.1 only describes monthly.

**Kept places an intent by `resolvedAt ?? createdAt`.** §6.3 says "within the
current period" without saying which date. A released hold belongs to the
period it was released in; a decline nobody acted on belongs to the period it
was asked in.

**`release` is not a legal action from `OPEN`.** §6.4's lifecycle diagram does
not include it. Kept means money that survived a wait or a refusal, and letting
an intent go the same second it was allowed involved neither. Nothing is lost:
a declined intent already counts toward Kept while it sits in `OPEN`.

**`BudgetState` carries a discretionary companion to `dailyBurn`.** §6.2 fixes
`dailyBurn` as `spentTotal / days elapsed`, and rent landing on day one makes
that project a number nobody should act on — AED 45,749 against an income of
18,000, in the seeded dataset. The specified figure is kept exactly as
specified; `spentDiscretionary`, `dailyBurnDiscretionary` and
`projectedEndSpendDiscretionary` are added alongside it, and the burn line
reads those. Redefining `dailyBurn` would have been the quieter change and the
wrong one.

## Single user

**`getCurrentUser()` resolves the first `User` row.** §1 rules out auth
providers, so there is no session to read. Every server path goes through one
function, so the day this grows a session there is exactly one place to change.
`PUT /api/policy` creates that row when it does not exist, because onboarding is
the entry point for a fresh install.

## AI layer

**`AI_UNAVAILABLE` returns 503 and creates no `Intent`; the arithmetic fallback
runs in the browser.** §8 says the API must not fabricate a verdict; §11.3 says
the screen shows an arithmetic verdict "computed locally from `BudgetState`".
Split that way, both hold: the engine produced no verdict so there is nothing to
record, and `/ask` computes the arithmetic from the `BudgetState` the server
already sent it. That fallback lives in `src/lib/arithmetic-verdict.ts`, which
imports nothing from the Anthropic SDK, so the SDK cannot reach a client bundle.

**The `UsageCounter` daily cap covers parsing as well as verdicts.** §7.4 names
`VERDICT_DAILY_LIMIT`; the same limit is applied to the `parse` counter, since an
unbounded import is the more expensive runaway of the two.

**Eval scoring lives in its own module with its own tests.** An eval harness
that miscounts reports green while the prompt degrades. An empty suite scores
0, not a free 100%, because a fixture file that failed to load must not read as
success.

**Eval fixtures are generated by `evals/build-fixtures.ts`.** Every
`budget_state` in them is internally consistent — `safeToSpend` really is
income minus bills minus spend minus holds — and `evals/run.ts` re-checks that
before spending a token. A fixture whose arithmetic does not add up tests
nothing. Writing them surfaced three conflicts worth keeping out of the suite:
`R-01` ("nothing over 200 without a 48 hour wait") contradicted every boundary
case expecting an `allow` above 200, so the boundary cases run without it;
`R-02` ("no food delivery on a weekday") made the delivery holds ambiguous, so
those notes name a weekend; and one expectation was simply wrong.

**Merchant match is reported but does not gate the parse suite.** §14 sets the
exit criterion at 95% on parse *amounts*. Merchant drift is printed as a
secondary signal so it is visible without failing a build over a title-case
difference.

## Import

**Idempotency has two independent guards.** Netlify retries a failed background
function after 1 minute and again after 2, so a second run is the normal failure
path. Only rows still `PENDING` are processed, *and* rows are written with
`skipDuplicates` against the composite unique on `Transaction`. The integration
suite tests both, including the case where every row is forced back to `PENDING`
to remove the first guard and check the second holds alone.

**A transaction's `reference` is the bank's own if present, otherwise
`SMS-<sha1(sourceText)[0:16]>`.** Deterministic, so the same message produces
the same key on a retry. Re-importing the same dateless message in a *different*
batch can still create a second row: the fallback date is the batch's
`createdAt`, and two separate pastes are genuinely ambiguous. §20 requires the
same *batch* to add zero rows, which it does.

**`POST /api/import` runs the batch in-process when no origin is configured.**
Netlify supplies `URL`/`DEPLOY_PRIME_URL`; locally there is no background
runtime, so the work is dispatched without awaiting it and the route still
returns 202 immediately. This makes the flow exercisable end to end under
`next dev`.

**CSV rows are converted to the same message strings the SMS parser reads.**
One pipeline rather than two, so corrections, idempotency and confidence all
behave identically whichever way the data arrived.

## Sweep

**Recurring-charge detection matches existing bills on amount and due day, not
label.** Running the sweep against the seeded data detected `LANDLORD TRANSFER`
as a new bill when `Rent` already covered that payment — which would have
counted AED 7,000 twice in `committedBills` and quietly shrunk safe-to-spend.
The statement never spells a bill the way the user did, so labels are not
comparable. A hand-made bill is never overwritten by a detected one.

**Gaps under a day are not recurring.** Three charges at the same merchant
within an hour are a till splitting a basket, not a monthly bill.

## Design

**The burn line's "crossing" means the line goes above the even rate and stays
above.** The first implementation marked any momentary excursion, which
labelled a period projecting AED 2,350 against a 6,300 allowance as crossing on
day one. A projected overspend that recovers is not a projected overspend.

**The even-rate reference is 35% of income.** Both the demo burn line and
`/insights` derive it the same way, from the user's own income, so the two
charts in the product mean the same thing. It is a discretionary allowance, not
a claim about what anyone should spend.

**`LedgerRow`'s borders sit on a wrapper, not on the row.** The expanded panel
has to be a sibling of the row control: inputs nested inside a `<button>` are
invalid HTML and unreachable by keyboard.

**The top bar's one square button is `Ask`.** §10 calls for one button without
saying which. The frame should always offer the single thing the app is for.

**`/ledger`'s running column walks down from the period total.** Rows arrive
newest first, so accumulating from the period's `spentTotal` makes the column
exact from the first page and stops it shifting as more pages load.

**Playwright honours `CHROMIUM_PATH` when set.** Lets an image with a
pre-provisioned Chromium run the suite without downloading a second copy.

## What was not built

Nothing in §1.1. No investment or lending guidance, no bank integrations, no
receipt OCR, no multi-currency, no social features, no notifications beyond
in-app.

## Tooling

**No ESLint.** `next lint` is deprecated in Next 15.5 and prompts
interactively, which makes it a script that hangs rather than one that runs.
TypeScript `strict` with `noUncheckedIndexedAccess`, plus `npm run typecheck`
in CI, covers what mattered here. `eslint.ignoreDuringBuilds` stays set so
adding a config later cannot silently start gating deploys.

**Seed idempotency is delete-then-rebuild.** The seeded user is removed —
cascading to everything it owns — and rewritten from a fixed PRNG seed. Upserts
would not have been enough: the dataset is anchored to "the last 90 days", so
its dates move with the calendar and an upsert key containing `occurredAt`
would accumulate a new copy every day.

## Deployment

**Functions stay at `src/netlify/functions`; `netlify.toml` sets `directory`.**
§3 of the build specification fixes that path, so the config moved rather than
the folder. Netlify's default is `netlify/functions` at the repository root,
and the failure mode when it is wrong is silence: no cron, no background
import, no error.

**`config.path` was removed from `import-background`.** The function is already
served at `/.netlify/functions/import-background` by virtue of its filename;
`path` declares a *custom* route, and pointing one at the reserved `/.netlify/`
prefix duplicated the built-in endpoint for no gain. Bundling it both ways
confirmed the `-background` suffix alone still yields
`invocationMode: "background"`.

**`node_bundler = "esbuild"` is kept but is inert here.** §4.2 specifies it, and
it would apply to any future v1 function. Both current functions are v2 ESM,
which zip-it-and-ship-it always bundles with `nft` — verified by requesting
esbuild and reading back `bundler: "nft"`.

**The cron is declared twice, on purpose, and checked.** `netlify.toml` carries
it because §4.2 says so; the function's own `config` export carries it because
that is the v2 idiom and is what the bundler reads straight from the file. Two
sources can drift, so `check:netlify` fails when they disagree.

**`HOLD_WINDOW_MS` moved from `lib/env.ts` to `lib/intent-machine.ts`.** The
client-side environment audit found that `intent-machine` — reachable from the
`HoldCountdown` client component — imported the server env module for a
constant that was never env-derived, which put `APP_TIMEZONE` and
`VERDICT_DAILY_LIMIT` into the browser bundle. No secret leaked, since Next
replaces non-public `process.env` reads with `undefined`, but server env
plumbing should not ship at all. The unused `requireAnthropicKey` was dropped
in the same pass.

**Migrations run in the Netlify build, scoped to the production context.**
The alternative considered was a separate CI job gated on the production
branch. Keeping it in the build wins on one decisive point: **ordering**. The
migration finishes immediately before the build that ships the code depending
on it, in the same sequential command, with no coordination. Moving it to
GitHub Actions puts two systems on one database that both trigger on a push to
`main` and have no ordering guarantee between them — the new code can deploy
before its migration lands. Buying that guarantee back means either
expand-contract discipline on every migration or gating Netlify's publish on
the Actions run, which is a lot of machinery for a single-user app with one
database.

What was genuinely wrong was not *where* it ran but *how often*: the command
was the default for every deploy context, so a deploy preview or a branch
deploy would have rewritten the production schema. That is fixed by scoping —
`[build]` no longer migrates, `[context.production]` does, and
`check:netlify` fails if that ever inverts.

One premise worth correcting: a failed migration does not take the site down.
A failed Netlify build is simply not published, so the previous deploy stays
live and serving. The blast radius is "the deploy does not ship", not "the site
is gone". `migrate deploy` is also a no-op when nothing is pending, so the
majority of builds mutate nothing at all.

This would flip if the project grew branch databases, more than one
environment, or destructive migrations needing a controlled window — at that
point a gated, manually-triggerable job is worth the coordination cost.

**The preflight loads `.env` the way the Prisma CLI does.** Present-only, never
overriding a real environment variable. Without it the preflight and the very
next command in the build disagreed locally: Prisma read `.env` and succeeded
while the preflight, seeing only `process.env`, reported the variable missing.
On Netlify there is no `.env` and it is a no-op; the point is that running the
build command locally behaves like the deploy.

**`ANTHROPIC_API_KEY` is a preflight warning at build time, not a failure.**
It is scoped to Functions only, which is correct, so a build cannot see it —
failing the build over its absence would punish the right configuration. It is
a hard failure under `--runtime`, which is the mode that checks what a deployed
function needs.
